# Local image build check

`build-local.sh SOURCE_ARCHIVE EXPECTED_SHA256 OUTPUT_DIR SOURCE_COMMIT` builds the five official production Dockerfiles for `linux/amd64` from a caller-curated, frozen repository archive. The archive must have the repository root at its root and exclude secrets and local dependencies. The script validates its SHA-256, extracts into a temporary directory, rejects common private files, uses the default same-origin frontend build settings and records logs, image IDs, sizes, architecture, and durations in an initially empty output directory. The 40-character lowercase `SOURCE_COMMIT` is passed to the frontend Dockerfiles for their fixed public-source link; the operator must establish that it is the public commit corresponding to the archive. It creates local tags only; it never pushes, starts services, or deploys. API, worker, beat worker, and migrator share the backend image and use different runtime entrypoints. Each build has a 3600-second default timeout; `PLANE_BUILD_TIMEOUT_SECONDS` can lower it.

The archive digest identifies the source snapshot; it does not make images bit-reproducible. Official Dockerfiles use mutable base tags, package repositories and network downloads. Docker's standard CA validation remains enabled. An operator must independently review the archive for sensitive contents; filename checks cannot prove it is secret-free.

Browser build defaults use an empty same-origin API URL, `/god-mode` for admin, `/spaces` for space, and `/live` for live. Space's server-side public issue metadata loader additionally needs runtime `PLANE_INTERNAL_API_ORIGIN` set to an explicitly trusted HTTP(S) origin such as `http://api:8000` on the private application network. It accepts only an origin, not a path, credentials, query, or fragment; redirects are refused. This server-only value is not derived from the request Host or forwarded headers and is never used as a browser URL. If omitted or invalid, public pages fall back to generic metadata. Verify internal networking, permissions, and actual metadata at deployment; image building alone does not validate the complete application.

## Five-image build, scan and publish

`.github/workflows/parksi-release-images.yml` is a local proposal for a push to the exact `Lparksi/plane` branch `release/parksi-ce-20261120`. It builds web, admin, space, live and backend on separate `linux/amd64` runners from the triggering commit's `git archive`. Earlier CI runs were scan-only and did not publish. This proposed version transfers the five scanned and smoked archives as one-day GitHub Actions artifacts and publishes only after every matrix build succeeds. Artifacts are accessible under the repository's Actions access policy. The build job has `contents: read`; the separate publish job has `packages: write`. Checkout credentials are not persisted. API, worker, beat and migrator share the backend image. No deployment is performed.

Each job builds once, exports a private temporary archive, and checks that archive with the official Trivy v0.76.2 binary after verifying the pinned release SHA-256. Trivy runs in a local `FROM scratch` container without network, as non-root, with a read-only root filesystem and no Docker socket; the image and scanner configuration are mounted read-only. The vendor `secret` and `image-config` secret scanners run offline with `skip-patterns: []` and the 13 version-specific broad built-in allow rules disabled. Only the independently checked, exact upstream example fixtures described below are exempted; unknown findings, scanner errors, incomplete reports, image-ID mismatches and changed archive checksums fail the job. Raw reports and scan output are removed; public job output is restricted to fixed messages and validated digests. Each component runs isolated smoke tests on the same image ID before export and scanning; backend uses temporary, digest-pinned database, queue, cache and S3 services on an isolated network. These services are not included in the image artifact.

Trivy's documented image scanner can skip base layers and does not guarantee coverage of every binary or encoded/nested format. A clean result is a heuristic check, not proof that every layer is free of secrets. The verifier accepts a reported private-key match only for exact happy-dom 21.0.4 source/lib paths or the Space server bundle; it binds the report to the image config ID, ordered diff IDs, actual compressed and uncompressed layer digests, exact path and reporting range, and a unique complete public example block hash. Both source and compiled library files must also match their independently verified upstream full-file hashes, and the lockfile must contain the verified upstream package integrity. The bundle may differ between builds but must contain exactly one matching example block. Missing, ambiguous, altered or additional findings fail closed. A single verified zod 4.6.7 test source file is removed after the application build and before the final image COPY; happy-dom runtime files are not removed. The backend verifier similarly permits only two independently checked exact upstream documentation fixtures, and rejects additional or changed findings. These verifiers are source-controlled alongside the workflow, not an independent trust root. Prior local images were only rehearsals; each CI build must be evaluated from its own report and archive.

The temporary Dockerfile transformation pins the known official `linux/amd64` node, Caddy and Python base manifests and the Caddy ratelimit version. It refuses unexpected mutable `FROM` entries. Go transitive dependencies, APK repository updates, the BuildKit frontend and runner remain mutable, so the result is not guaranteed byte-for-byte reproducible. This is a secret scan only, with no unrequested CVE severity threshold. Local image config IDs and archive SHA-256 values are not OCI registry manifest digests.

The five matrix jobs run at most two at a time. A 6 GiB initial free-space check and 4 GiB compressed archive limit do not guarantee that a 14 GiB runner can complete. GitHub's default concurrency queue can replace an older pending run without canceling the running one. Builds may incur Actions costs. The workflow and source are controlled by the same branch and are not an independently controlled trust root. A single random 128-bit run suffix gives each component a new GHCR package name; the full commit is the tag. The publication matrix is not atomic, so a failure can leave a partial set: inspect the registry before any retry. GHCR package creation permissions and visibility remain to be verified. The workflow has not yet been validated end to end and does not establish deployment readiness.

# Web-only isolated build experiment

This is a proposed experiment, not a successful CI run, a security audit, or a deployment approval. A push that changes `.github/workflows/parksi-web-experiment.yml` on `release/parksi-ce-20261120` would start one Web job if Actions is enabled. It uses the triggering commit's `git archive`, a local-only image, no image/artifact upload and no deployment. The older five-image `parksi-audit-only.yml` is switched to manual dispatch to avoid rerunning that matrix on the same push. GitHub requires the workflow to exist on the default branch before manual dispatch can be offered; no default-branch change is made here. The separate proposed GHCR publication gate remains closed.

The experimental Dockerfile is checked against the official Web Dockerfile plus the explicitly reviewed changes. Its three selected Linux/amd64 image manifests are:

- `node:22-alpine@sha256:12f54cafa58d0e96554ae05871e29663ff7241836377dc9a7916449b8adb062c`
- `caddy:2.11.7-builder-alpine@sha256:420db7c0f6927c7e8140c666628915fb4a9141282fc5c344716ebf3879fe8f9b`
- `caddy:2.11.4-alpine@sha256:040e9f7480b80b6d4a7e5013a21159b950a63dcbdb956e38abe2387fb28d9ec0`

These digests bind bytes; they are not signature verification or proof of safety. The recipe pins `caddy-ratelimit` to `v0.1.0`, checks the resulting Go binary's reported module version, and copies Caddyfile with mode 0644. It does **not** lock the entire Go dependency graph: `go get`, `go mod tidy`, APK repository state and upgrades, and the BuildKit Dockerfile frontend remain mutable. The JavaScript and custom Caddy binary are not independently reproduced. The workflow therefore reports `OS_DELTA_UNVERIFIED`; it must not be interpreted as a fully reproducible build or a verified application-layer provenance.

The proposed job records only bounded source/archive/recipe/lock/Caddyfile/binary/served-JS hashes, the image configuration ID and the number of runtime-base-prefix and later layers. It checks the Caddyfile bytes against the archived source, the runtime base prefix against the pinned local base, and serves the root and source-link JavaScript from the exact image in a no-network, read-only, non-root container. The latter is an HTTP and static-asset check, not a browser interaction or a complete application test. Failure at any stage is a failure, not evidence of safety. Job/tool output is kept local and removed; only fixed results and validated digests reach the job log. The 6 GiB initial free-space check cannot guarantee that a 14 GiB runner will not exhaust disk.

The workflow and build recipe come from the same source commit. They do not constitute an independent trust root or independently verify a secret scanner; branch protection and an independently controlled reviewed executor would be required for stronger assurance. A build can still execute source and download network dependencies; do not pass production secrets, credentials, a Docker socket, or private data to application containers. Prior local testing of an older image established an isolated HTTP response as root with capabilities dropped, but its non-root run failed; the new recipe has **not** yet run and non-root behavior remains to be demonstrated.
